# Technical SEO — Phase 2

**Site:** https://paramiyer.github.io/resume-site/ · **Updated:** 2026-08-29

The site is server-rendered static HTML with no client-side routing, so
crawlability was never the problem. The problem was that there was one URL
carrying no machine-readable identity. This phase fixes the identity and the
crawl surface, and settles the architecture question Phase 3 depends on.

---

## Canonical strategy

Single canonical origin: `https://paramiyer.github.io/resume-site/` — always with
the trailing slash, always absolute.

GitHub Pages serves the project site only on that host, so there is no
www/apex or http/https split to reconcile. Every absolute URL in metadata,
structured data and the sitemap uses the `SITE` constant in
`scripts/build-stats.mjs`; changing that one value moves the whole site,
including if a custom domain is added later.

`404.html` carries `noindex` and deliberately no canonical.

## Metadata strategy

Per page, all hand-authored except where noted:

| Element | Value |
|---|---|
| `<title>` | `Parameshwaran Iyer \| Principal AI Architect & Enterprise AI Leader` |
| `description` | positioning + sectors + region, ~185 chars |
| `canonical` | absolute, trailing slash |
| `theme-color` | dark/light variants matching the palette |
| icons | `favicon.svg`, `apple-touch-icon.png`, `site.webmanifest` |
| OpenGraph | `type=profile`, url, title, description, image (+w/h/alt), `profile:first_name`, `profile:last_name` |
| Twitter | `summary_large_image` |

**Titles and descriptions must stay unique per route.** With one route that is
trivial; from Phase 3 it becomes a rule the page generator has to enforce.

### Social image

`og-image.png`, 1200×630, generated from `scripts/og-card.html` by rendering it
in headless Chrome:

```bash
python3 -m http.server 8797 &
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --hide-scrollbars --window-size=1200,630 \
  --screenshot=og-image.png "http://localhost:8797/scripts/og-card.html"
```

Deliberately **not** part of CI — Chrome is not available on the runner, and the
card only changes when the positioning changes. Regenerate by hand and commit.

## Structured-data architecture

One `@graph` in `index.html` between `<!-- GEN:JSONLD -->` markers, generated by
`renderJsonLd()` so `dateModified` tracks the weekly refresh.

| Node | `@id` | Purpose |
|---|---|---|
| `Person` | `#person` | the entity everything else points at |
| `ProfilePage` | `#profilepage` | `mainEntity` → Person, `dateModified` |
| `WebSite` | `#website` | `author` → Person |

### Why there is no `jobTitle` and no `worksFor`

This is the one deliberate omission and it is worth stating plainly.

The positioning is *Principal AI Architect*. The role actually held is **AI
Consultant**, and the page says so in Career Journey. Putting the positioning in
`jobTitle` would contradict the page's own content and assert a title never held —
exactly what the programme's factual-integrity rule prohibits. `worksFor` is
omitted for the same reason: current employment is not asserted.

Instead:

- **`description`** carries the positioning as prose, where it is a claim about
  capability rather than a title.
- **`hasOccupation`** → `Occupation { name: "Enterprise AI Architect",
  occupationLocation: United Arab Emirates }`. This describes the occupation
  without claiming an employer relationship, which is the accurate shape.

If a role with that title is ever held, add `jobTitle` then — not before.

### Verified properties only

- `alumniOf` — Pennsylvania State University, University of Mumbai
- `address` — `addressCountry: AE` only. No city: the site says "Based in the
  UAE" and inventing Dubai or Abu Dhabi would be fabrication
- `knowsAbout` — 11 entries, each evidenced by a section of the page
- `sameAs` — 4 profiles, **all verified HTTP 200**: LinkedIn, GitHub, Google
  Scholar, OpenAlex

No `award`, `hasCredential` or `memberOf`: the Phase 0 inventory found no
evidence for any, and structured data is the worst place to guess.

## Sitemap

`sitemap.xml` is generated from the `ROUTES` array in `scripts/build-stats.mjs`.
One entry today. **Phase 3 adds routes to that array and the sitemap follows** —
no separate list to forget.

`lastmod` is date-only. A full timestamp would change on every run and break
generator idempotence, which is a property the weekly job depends on.

## robots.txt

Allows everything, points at the sitemap. Nothing is disallowed: `scripts/` and
`data/` are published on purpose — they are the automation the page credits, and
they are safe to read.

`docs/` is not disallowed because it is **not deployed at all** — the workflow
stages `_site/` from an explicit file list rather than uploading the repo root.
Exclusion by absence beats exclusion by request.

## Indexable vs non-indexable

| Route | Indexable |
|---|---|
| `/` | yes |
| `/404.html` | no — `noindex` |
| `/scripts/*`, `/data/*` | served, not linked, not in sitemap |

## Accessibility and Core Web Vitals work in this phase

- **Skip link** to `#main`, visible on focus
- **Explicit `width`/`height` on the avatar** — removes the layout shift it was
  causing, which is a CLS input
- `fetchpriority="high"` on the avatar, the only above-the-fold image
- Heading order verified h1 → h2 → h3 with no skips

## Where verification tokens go

Nothing is fabricated here. When the accounts are created:

| Service | Where |
|---|---|
| Google Search Console | `<meta name="google-site-verification" content="…">` in the head of `index.html`, or a `google*.html` file added to the staging list in `static.yml` |
| Bing Webmaster Tools | `<meta name="msvalidate.01" content="…">`, same place |
| IndexNow | `<key>.txt` at the root plus the same key in the staging list |

Phase 6 covers submission.

## Architecture decision — multi-page, without a framework

**Decision: extend the existing generator into a small multi-page builder. Do not
adopt a framework.**

Phase 3 needs roughly 12–20 routes. Hand-authoring them is not viable: each page
would duplicate ~40 head tags and ~300 lines of CSS, and a palette change would
mean editing every file. That breaks at about the third page.

Adopting Astro/Next/Eleventy would solve it, but costs the property that makes
this repo pleasant — **zero dependencies, no lockfile, no install step, a CI job
that is `node scripts/…` and nothing else**. That is worth keeping.

The middle path, and the one this repo already half-implements:

- A `layout()` function owning `<head>`, shared CSS, nav and footer
- Pages as data — front-matter-ish objects with `slug`, `title`, `description`,
  `body`
- The existing `<!-- GEN:x -->` marker/inject idiom kept for the homepage, so
  hand-written prose stays hand-written
- `ROUTES` drives the sitemap, so a new page is automatically crawlable
- Output written to the repo root and staged by the same workflow

Estimated ~150 lines on top of what exists. No dependencies added. The one real
cost is a hand-rolled templating layer, which is acceptable at this size and
would not be at ten times it.

**Revisit if** the page count passes ~30, content editors other than Param appear,
or per-page interactivity is needed. None is true today.
